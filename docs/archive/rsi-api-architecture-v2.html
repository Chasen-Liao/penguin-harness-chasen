RSI API 架构设计与统一协议规范 Design doc V2 · Protocol v1
核心结论 全景闭环 统一协议规范 三步工作台 落地路线 ←→ 切换步骤

让外部 Agent Harness 的 Skill 自进化可量化、可验证、可回退

核心结论：让 AI 修改自己的 Skill 并不难，难的是证明改完更好，并且在信息不完整时仍能诚实地说清「看到了什么、缺了什么」。RSI API V2 把「日志沉淀 → 基准构建 → 离线优化 → 量化验证 → 安全回写」定义为一套跨 Harness 协议：一个外部 session 对应一条逻辑 trace；历史按 ID 拉取、运行中增量推送，两条路径以 revision 仲裁重复、乱序与旧快照；每次读取都带可见性与缺口；Skill 以完整目录包传输，验证凭证绑定候选包摘要；只有验证凭证处于放行态且无 base_hashes / 摘要冲突时，才允许写回。

S背景

Agent 表现依赖 Skill、Hook、指令文件等 Harness 配置；真实交互是构建评测尺子的原料。

C冲突

黑盒自改缺少验证；来源常常只能提供部分信息，权限、策略、能力与离线状态都会造成缺口。把「没看到」当「没有」，后续结论全部失真。

Q核心问题

如何用一套跨 Harness 协议，让采集、评测、优化、回写形成可验证、可回滚、可解释缺口的闭环？

A协议方案

四根支柱：可验证闭环；双路径采集 + 版本化 SessionSnapshot；薄 Adapter + 能力/可见性声明；三步工作台 + 缺口可视化。

01 / 自进化全流程设计

从「黑盒盲改」升级为「双路径采集 + 验后上线」的完整闭环

图分三层：外部 Harness → Adapter（来源机器上的薄翻译层）→ 内部自进化平台（含 RSI 接收端、存储、Benchmark、优化与 Proof 闸门）；RSI 接收端属于内部平台，不是单独的第三层。历史按 ID traces.pull 纯读，运行中由 Adapter traces.push 增量推送，两条路径汇入同一 rsi_* 独立存储；离线优化后经 VerificationProof 闸门，才允许 skills.push 灰度回写。

02 / RSI API 统一协议规范 (v1)

标准方法命名规则、全量核心字段定义与多系统适配契约

以 SessionSnapshot 为唯一会话单位，用 revision + 两个摘要仲裁新旧，用 visibility/gaps/sync 描述证据边界，用 VerificationProof 约束写回。

双路径采集、离线不丢

历史按 ID traces.pull 纯读，运行中由 Adapter traces.push 增量推送；Hook 只登记变化，不阻塞外部 Harness。

一个 session 一条 trace

身份是 (source_id, session_id)，版本由 Adapter 单调分配；重复、乱序与旧快照都用同一套 revision 规则仲裁。

可见性与缺口显式

五域四态；不可见就省略字段并记 gaps，unknown 不得写成 0 或空数组；交付延迟只放 sync。

验证入契约、瘦 Adapter

skills.push 必带 verification + base_hashes；Adapter 只验放行态、候选摘要与冲突，复杂打分留在平台侧。

标准方法总表（9 个核心方法 + 2 个可选扩展）

类别 标准方法名 提供方 HTTP 路由（统一前缀 /api/rsi/v1） 职责说明
能力发现 harness.info Adapter GET /info 声明来源类型、source_id、连接方向、能力位与默认可见性
Hook 管理 hooks.install / status / uninstall Adapter POST /hooks · GET /hooks/status · DELETE /hooks/:hook_id 挂载、健康检查与卸载；四态 + trust_status/current_hash

轨迹发现 traces.list Adapter POST /traces/list 按 from/to + page/page_size 发现会话摘要
轨迹写入 traces.push RSI 接收端 POST /traces/push delta/snapshot 推送；事务提交后 ack
Skill 拉取 skills.pull Adapter POST /skills/pull 拉完整 SkillBundle[] + content_sha256，锁定基线 v0
Skill 推送 skills.push Adapter POST /skills/push 校验 verification/base_hashes/候选摘要后备份并写入

鉴权约定：ingest token 只写本连接 trace；control token 读 trace/skill，可选 skills:write、eval:run、hooks:read、hooks:manage；不复用管理员 token 或单个 Agent API key。

核心数据模型、错误码与可选扩展速查（点击切换）

harness.info 在接入握手时调用，声明来源能力、连接方向与默认可见性。

字段名类型必填说明
protocol_version"v1"是协议版本，与路径 /api/rsi/v1 一致
source_idstring是Adapter 稳定标识；机器 + Harness home + profile，跨重启不变
harness_type"codex" | "claude_code" | "opencode" | "penguin" | "custom"是来源类型
connection_modesArray<"push" | "pull">是两项独立，可同时声明；仅出站时只有 push
access_level"white_box" | "gray_box" | "black_box"是层级摘要；事实以 capabilities 为准
capabilitiesobject是traces/skills/hooks/eval 逐项能力；skills 含 scopes/writable
default_visibilityobject是五域默认可见性；每次快照可更弱，不能更强

Hook 四态显式；trust_status 是来源事实，pending_trust 是 RSI 协议状态。

对象 / 字段类型必填说明
hooks.install.hook_idstring条件可重试调用方必须提供；省略时按 (connection, agent_id, events) 生成确定性 id
hooks.install.eventsArray<string>是session_start/user_prompt/pre_tool_use/post_tool_use/stop/interrupt/pre_compact/post_compact/session_end/subagent_start/subagent_stop
hooks.install.delivery{mode: "native_log" | "local_buffer", buffer_dir?}是native_log 只记去哪儿读；local_buffer 先落盘再推送
HookStatus.status"not_installed" | "pending_trust" | "active" | "broken"是四态；pending_trust 需要人工信任
HookStatus.trust_status"managed" | "untrusted" | "trusted" | "modified"否来源的 trust 事实；与 pending_trust 不互相替代
HookStatus.current_hashstring否当前 Hook 定义摘要；变化回到 pending_trust
HookStatus.installed_pathsstring[]是来源机器上被修改的配置路径
HookStatus.pending_countnumber否本地缓冲中尚未 ack 的估算数量；不是完整性证明
DeliveryStatus.pending_unit"revision" | "push_batch" | "turn"是默认 push_batch；与 SyncState 分开
DeliveryStatus.source_revisioninteger是Adapter 当前最新 revision

traces.pull 只传 session_id；traces.push 由 RSI 接收端提供，delta 只追加精确后缀，snapshot 表达完整替换。

字段名类型必填说明
session_idstring是来源原生 ID，opaque；同一 source_id 内唯一
source_idstring是内部键 (source_id, session_id)
revisioninteger是Adapter 单调分配并跨重启持久化
content_sha256string是有效可见 records 的 JCS 摘要
metadata_sha256string是固定元数据字段集摘要；幂等键的一半
recordsAmspRecord[]是按分片索引 + 行序的可见记录；完整 session_meta 保留
visibilityobject是messages/tool_calls/skill_usage/subagents/raw_log 五域
gapsGap[]否内容/授权缺口；partial 必带
syncSyncState否只由 RSI 填写；交付延迟不写 gaps
active_skills / skill_evidencestring[] / SkillEvidence[]否只收已加载/有使用证据；安装清单不算
child_sessionsChildRef[]否只列直接子会话；不可读保留 readable:false + 原因
raw_pathstring[]否来源机器路径；RSI 永不打开

SkillBundle 是完整目录快照；协议 v1 只支持 kind:"skill"、单包 merge。写入前必须校验 proof + base_hashes + 候选摘要。

字段名类型必填说明
namestring是目录名与身份；^[A-Za-z0-9_-]+$
kind"skill"是v1 不支持 instruction bundle
content_sha256string是完整目录包摘要；Adapter 从 files[] 重算
filesArray<{rel_path, encoding, content}>是必须含根 SKILL.md；保留 scripts/references 子目录
skills.push.request_idstring是幂等键；同 id 不同 payload 返回 409 request_id_conflict
base_hashesRecord<string, string | "absent">是覆盖每个 name；"absent" 表示拉取时不存在
verificationVerificationProof是放行态 + 候选摘要 + target + coverage
trust_state"active" | "pending_trust" | "rejected"是（响应）applied 是写入；trust_state 是生效
backup_idstring条件写入前生成；backup_before_write=false 时禁用回滚

Proof 是写回的审计凭证；Adapter 只校验结构与放行态，不重跑评测。自动放行要求覆盖 predicate 与 runs 对称，否则只能 override_by_user。

字段名类型必填说明
target{agent_id, source_id, harness_type}是凭证绑定的目标；与连接不一致 422
proof_sha256string是proof 去自身后的 JCS 摘要
benchmark_content_sha256string是尺子内容摘要；两侧必须同值
baseline / candidateProofSide是各带 evaluation_id、bundle_sha256、metrics、runs_per_case、data_coverage
delta{score, cost_usd?, duration_ms?}是candidate − baseline
gate_policy"score_strict" | "pareto"是默认 score_strict
pareto_improvedboolean是每个可比维度不差且至少一项严格更好
regressionsRegressionEntry[]是逐题回归数组，不是计数
gate_decision"approved" | "override_by_user"是只有这两个值放行
overrideobject | null条件{approved_by, approved_at, reason, acknowledged_regressions, proof_sha256}
candidate_hashesRecord<string,string>是名称→候选包摘要；键集合等于 skills[].name

错误信封 {error:{code,message,phase,retryable,repair_hint,details}}；错误码闭合，一码固定一个 HTTP 状态。

03 / 自进化工作台迭代计划

三步完成进化，效果可见、异常可修

工作台把复杂流程收敛为递进式三步：先接入与沉淀，再出题与评估，最后离线优化与校验上线。所有图表都先展示证据边界，再允许下一步；失败统一以 RsiError 触达人与 Agent。

STEP 01

接入与沉淀数据

harness.info 读取能力与可见性；有历史先 traces.list / traces.pull；需要运行中更新再 hooks.install，并用 traces.push 增量入库。

STEP 02

出题与评估

在 rsi-workbench 的「出题」中生成或导入 Benchmark，在「评估」中取得基线；冻结 (source_id, session_id, revision, content_sha256) 并 pin。

STEP 03

优化与校验上线

skills.pull 备份 v0 后离线迭代，生成 VerificationProof；通过覆盖 predicate 与 runs 对称后，skills.push 灰度写入，异常 skills.rollback。
