RSI API · design document

让 Skill 的自进化，
变得可验证。

一个外部 session 对应一条逻辑 trace。历史按 ID 拉取，运行中增量推送； 每次读取都带可见性与缺口；Skill 以完整目录包传输，Proof 放行后才写回。

01 / problem

问题不在改，而在证明改得更好

AI 直接编辑 Skill 已经没有技术门槛。缺少的是基线、覆盖与回滚：改完到底更好，还是只对个别样例过拟合？

01

黑盒自改

一次改动可能修好一个场景，却在另一个高频场景引入回归。没有同一把尺子的前后对照，看到的只是观感。

02

信息不完整

日志会截断，权限会缺失，运行期事件只在当下出现，来源可能根本不支持重读历史。把“没看到”当成“没有”，后面的结论都会失真。

03

每个 Harness 一套

Codex、Claude Code、OpenCode 的 Hook、日志与 Skill 目录各不相同。每接一个来源就重写一遍采集与评测，无法比较。

RSI API 要解决的是：用同一套协议，把真实交互沉淀成可复现的 Benchmark，在离线环境优化 Skill，用可审计的 Proof 证明候选更好，再安全地写回。

02 / principles

八条设计原则

每一条都对应一个具体失效模式，不是口号。它们决定了后面的字段、方法与验收方式。

01

一个 session = 一条 trace

身份是 (source_id, session_id)；传输单位是版本化 SessionSnapshot，不是来源磁盘分片。

02

双路径采集

历史按 ID traces.pull（纯读），运行中由 Adapter traces.push；两路共用同一读取器与 revision 规则。

03

版本仲裁

revision 由 Adapter 单调分配；接收端按 (revision, content_sha256, metadata_sha256) 判重复、冲突与缺口。

04

可见性与缺口显式

五域 × 四态；不可见就省略字段并记 gaps，unknown 不得写成 0 或空数组。

05

完整 Skill 包

SkillBundle 是目录快照，content_sha256 是唯一包身份；v1 只做单包 merge，多 Skill 用多次 push。

06

先验证后回写

skills.push 必须带 VerificationProof；人工放行只绕过指标，不绕过基线哈希与摘要冲突。

07

错误可恢复

RsiError 闭合错误码；phase 决定恢复入口，retryable 决定是否重试。

08

只描述可验证事实

来源没提供的字段省略并记 gap；未持久化的流式片段不进快照；运行状态只有来源能证明时才写。

04 / model

一个 session，一条 trace，多个 revision

协议的单位不是日志文件，而是版本化快照。记录没有稳定 ID，所以用 session + revision + 两个摘要来定位版本。

身份与版本

一个外部 session 在 RSI 中始终只有一条逻辑 trace。身份是 (source_id, session_id)；session_id 是来源原生的 opaque ID，source_id 跨重启稳定。传输单位是某个 revision 的 SessionSnapshot。

revision 1 · snapshot首次导入；完整有效记录集合。
revision 2 · delta追加一个 turn；base_revision = 1；content/metadata 摘要。
revision 3 · snapshot可见性变化或历史重写；完整替换并重算摘要。

两个摘要，一个幂等键

content_sha256 覆盖有效可见记录，metadata_sha256 覆盖固定元数据；幂等键是 (revision, content_sha256, metadata_sha256)。重发按字节原样，派生字段不参与。

可见性不是布尔值

每个域都可能是“检查过、确实没有”“只读到一部分”“来源不支持”“还没检查”。unknown 不能写成 0 或空数组；partial 必须带 gap。

05 / protocol

11 个方法，四类动作

采集、Hook、Skill 与评测。每个方法一行，凭据与幂等性直接标在行上；不再把多个方法塞进同一个“方法组”。

方法提供方HTTP幂等凭据职责
harness.infoAdapterGET /info幂等control 读来源类型、source_id、方向、能力、默认可见性
hooks.installAdapterPOST /hooks按 hook_idcontrol + hooks:manage安装运行中采集；只在需要推送时调用
hooks.statusAdapterGET /hooks/status幂等control 读 + hooks:read四态、信任、待发数量、最近送达
hooks.uninstallAdapterDELETE /hooks/:id幂等control + hooks:manage卸载；默认保留未送达缓冲
traces.listAdapterPOST /traces/list幂等control 读按来源活跃时间与页码发现会话；默认含子会话
traces.pullAdapterPOST /traces/pull幂等control 读{session_id} → 一个完整 SessionSnapshot；纯读
traces.pushRSI 接收端POST /traces/pushrevision + 摘要ingest token推送 delta 或 snapshot；事务提交后才 ack
skills.pullAdapterPOST /skills/pull幂等control 读拉完整 Skill 目录包
skills.pushAdapterPOST /skills/push按 request_idcontrol + skills:write校验 proof、base_hashes、候选摘要后备份写入
skills.rollbackAdapterPOST /skills/rollback按 backup_idcontrol + skills:write按推前备份恢复；已恢复返回 already_restored
eval.runAdapterPOST /eval/run非幂等control + eval:run真机跑一个评测用例；trace 走 pull

错误也是协议的一部分。所有失败返回 RsiError { code, message, phase, retryable, repair_hint, details }；错误码闭合，一码固定一个 HTTP 状态与恢复入口。私有评分细则不会出现在 repair_hint 或 details 里。

06 / flows

三条关键路径

拉历史、推运行中、Skill 往返。三条路径都不要求调用方理解来源的日志文件、分片或页数。

  1. 发现：traces.list 按来源活跃时间与页码列出会话；默认包含子 Agent 会话。
  2. 读取：traces.pull({session_id}) 返回一个完整 SessionSnapshot；只传 ID，不传分页、时间或 workspace。
  3. 导入：平台把快照交给 RSI 接收端内部导入，复用 traces.push 的合并规则与事务 ack，保留 Adapter 分配的 revision。
  4. 确认：拿到 stored_revision 与两个摘要；Benchmark 可以 pin 这个 revision。
traces.listtraces.pullinternal importpin
  1. 触发：Hook 只登记“这个 session 变了”；不阻塞 Agent，也不改变行为。
  2. 读取：Adapter 用同一读取器拿到当前可见内容；日志晚于 Hook 落盘时可以重读。
  3. 推送：traces.push 发送 delta 或 snapshot，带 base_revision、revision 与两个摘要。
  4. 仲裁：接收端先按 revision 判新旧，再按摘要判同版本等价；重复返回 duplicate，旧版本 stale_ignored，缺口 revision_gap。
  5. 确认：只在事务提交后返回 stored；外围收到 ack 才清缓冲。
hooks.*traces.pushdelta / snapshotack
  1. 拉基线：skills.pull 拿完整目录包 v0，content_sha256 锁定基线。
  2. 离线优化：在隔离环境里跑 Benchmark，候选包 v1 不碰线上目录。
  3. 生成 Proof：绑定 Benchmark、运行配置、两侧指标、逐题回归与覆盖；Adapter 只校验结构与放行态。
  4. 写回：skills.push 校验 proof、base_hashes 与候选摘要；通过后备份、整目录替换，返回 trust_state。
  5. 观察与回滚：继续用 traces.* 观察；异常时 skills.rollback 按 backup_id 恢复，并校验当前 hash 防止覆盖别人的修改。
skills.pullVerificationProofskills.pushskills.rollback
07 / adapter

Adapter 是薄翻译层

白盒、灰盒、黑盒只是连接摘要；事实以 capabilities 逐项声明为准。先确定连接方向，再决定方法可用性。

白盒

完整会话、工具、Skill 加载/使用证据、子会话、原始日志。

  • 可读全部五域
  • 可装 Hook、可回写 Skill
  • 可提供 eval.run

灰盒

部分会话、工具或 Skill 证据；子会话可能不全。

  • 按能力位逐项开放
  • 关键域标记 partial 和缺口
  • 写回仍需 Proof

黑盒

只有输入/输出或调用结果；通常不能写回。

  • 至少提供 harness.info + traces.*
  • Hook / skills.push 通常 501
  • 只做输入/输出评分，不声称 Skill 归因
push 可用Adapter → RSI，可穿 NAT；运行中更新不依赖入站。
pull 可用RSI → Adapter，可读历史、拉 Skill、回写、评测；需要入站可达。
仅出站只有 traces.push；collection-only，隐藏第二三步自动动作。

Codex：19 种 ThreadItem 都有归宿

按组概括，逐项规则见 Markdown 设计文档。每一项要么映射到 AMSP 的 model_msg/event_msg，要么明确丢弃并记录 omitted_items；不能静默丢失，也不能伪造 gap。

08 / workbench

工作台：三步用户旅程，三个标签

接入与采集是平台前置，不占工作台标签。工作台本身是「出题 / 评估 / 优化」，推送与回滚是优化的收尾。

01 / 前置

接入与沉淀

选择来源与连接方向；导入已有会话；需要运行时更新时安装 Hook。显示访问层级、五域可见性、sync 与 gaps。

平台前置 · 不是标签
02 / 出题 + 评估

生成 Benchmark

筛选轨迹、生成或导入 Benchmark；冻结 revision/hash 并 pin；取得基线。显示参与会话、被排除原因与各域覆盖。

工作台：出题 / 评估
03 / 优化

优化与上线

运行优化方法，审阅榜单、帕累托与逐题 Diff；确认推送或回滚。显示候选包 hash、proof 覆盖、backup_id 与 trust_state。

工作台：优化
可见性徽标每个会话/case 显示五域状态；partial 显示缺口数，unknown 显示“未检查”。
缺口面板按 domain + reason 分组；区分可补拉、需重新授权、永久缺失。
覆盖警告关键评分域不一致时，v0/v1 分差不可直接比较；不同覆盖等级不画成一条趋势线。
Pareto分数 vs 成本/耗时；null 维度标“不可比较”；逐题回归单独列出。

异常恢复：按 RsiError 的 phase/retryable/repair_hint 分派到五类动作——补拉、重推/重建、重新授权、人工处置、接受降级。未列出的错误按 phase 默认恢复，不把可重试错误当永久失败。

09 / validation

首轮：在 Codex 上跑通一次真实闭环

不是演示协议，而是用同一 Benchmark 比较 v0/v1。验证场景覆盖主链路与协议边界；首轮实验在优化前冻结 held-out 与阈值。

场景看什么
按 ID 拉取快照 revision/摘要/可见性/records 顺序；pull 请求不传分页。
运行中更新App Server 通知流与 command Hook 两条路；pending_trust → active。
重复与乱序duplicate、revision_conflict、stale_ignored、revision_gap；丢 ack 后重发不重复。
部分可见与父子五域四态、gaps、unknown 不派生 0；不可读子保留引用，父不内联子树。
Skill 往返proof/base_hashes/候选摘要校验；冲突、重试、备份与 rollback。
首轮对照同一 Benchmark 上 v0/v1；分数、覆盖与 Proof 三者一致；有回归只能人工 override。

首轮实验契约：任务为隔离工作区修复预置失败的 TypeScript 测试；Skill 为合成 review-helper，v1 针对可测失败模式；Benchmark 6–8 个 case（3 dev + 3 held-out + 2 negative）；v0/v1 同 provider/model/thinking，runs 统一且两侧对称；每个 case 保留 fixture、runner 日志、rsi_* 存储行、scoreboard、proof 与 backup_id。

开放问题

AMCP 映射v1 以 AMSP 为唯一规范格式；AMCP 样例与映射尚未确认，可能影响核心记录模型。
数据治理Project 隔离、删除/导出/脱敏、来源删除后的保留与 purge 尚未定义；生产前必须补齐。
连接级 token scopeI11 是目标模型；当前实现仍是 admin token + 每 Agent API key，签发/轮换/迁移待落地。
后续版本instruction bundle、replace/prune、push-only 命令通道、黑盒评分回传不在 v1。
